Data dictionary and measurement levels

Unlike SPSS survey items, CRM variables are event timestamps, identifiers, categorical codes, and numeric activity measures. Their measurement level follows their business meaning, not whether they appear numeric in Excel.

Field Table Meaning Analysis role
alias roster, UserLoginHist User join key Nominal identifier; private
role roster Job category Nominal; REP is target group
APPLICATION UserLoginHist Login client or integration Nominal; distinguish automation
LOGINTIME UserLoginHist Login timestamp Temporal
CREATED_BY_ALIAS OppFieldHist Field-history actor Nominal; private

CREATEDDATE OppFieldHist Field-change timestamp Temporal

Data-quality audit

The roster can contain multiple rows for the same person after role changes. Joining activity records directly to all roster rows may multiply events. For this descriptive preparation, create a distinct set of REP aliases for population membership, and keep role-history interpretation separate. A temporal role-as-of-event join requires verified role dates and is not performed here.

roster_audit <- tibble(
  metric = c("Roster rows", "Distinct roster aliases", "REP role rows", "Distinct REP aliases", "REP aliases with multiple REP rows"),
  value = c(
    nrow(roster), n_distinct(roster$alias, na.rm = TRUE),
    sum(roster$role == "REP", na.rm = TRUE),
    n_distinct(roster$alias[roster$role == "REP"], na.rm = TRUE),
    roster |> filter(role == "REP") |> count(alias) |> filter(n > 1) |> nrow()
  )
)

Date conversion and missingness

Excel may represent dates as serial numbers or as date-time objects. Convert safely and verify date coverage before interpreting activity trends.

as_excel_datetime <- function(x) {
  if (inherits(x, "POSIXt")) return(as.POSIXct(x, tz = "UTC"))
  if (inherits(x, "Date")) return(as.POSIXct(x, tz = "UTC"))
  if (is.numeric(x)) return(as.POSIXct(x * 86400, origin = "1899-12-30", tz = "UTC"))
  suppressWarnings(as.POSIXct(x, tz = "UTC"))
}

logins <- logins |> mutate(login_dt = as_excel_datetime(LOGINTIME))
field_hist <- field_hist |> mutate(edit_dt = as_excel_datetime(CREATEDDATE))

Cleaning and transformation

Login events: separate integrations from human activity

The dictionary warns that integration accounts dominate raw login records. The first defensible filter is to retain only aliases in the REP roster. For a more conservative browser-oriented proxy, separately identify rows with APPLICATION containing Browser or Salesforce; this is provisional until the client confirms which applications represent genuine human activity. Neither proxy proves meaningful engagement.

rep_logins <- logins |> semi_join(rep_aliases, by = "alias") |>
  filter(!is.na(login_dt)) |>
  mutate(login_date = as.Date(login_dt),
         application_group = case_when(
           str_detect(coalesce(APPLICATION, ""), regex("Browser|Salesforce", ignore_case = TRUE)) ~ "Browser/Salesforce-labelled",
           TRUE ~ "Other application"
         ))

login_filter_audit <- tibble(
  stage = c("All login records", "REP-alias login records", "REP browser/Salesforce-labelled records"),
  events = c(nrow(logins), nrow(rep_logins), sum(rep_logins$application_group == "Browser/Salesforce-labelled"))
)

Opportunity field changes: candidate meaningful engagement

The field-history table contains changes by many actors, including creation/system-type events. Retain REP actors and distinguish FIELD == "created" from other field-history events. Do not call all other edits meaningful: the client must confirm which field names correspond to substantive sales work, and repeated events may describe a single action.

rep_edits <- field_hist |>
  semi_join(rep_aliases, by = c("CREATED_BY_ALIAS" = "alias")) |>
  filter(!is.na(edit_dt)) |>
  mutate(edit_date = as.Date(edit_dt),
         event_type = if_else(tolower(coalesce(FIELD, "")) == "created",
                              "Creation-labelled event", "Other field-history event"))

field_audit <- tibble(
  stage = c("All field-history records", "REP-actor field-history records", "REP non-creation field-history records"),
  events = c(nrow(field_hist), nrow(rep_edits), sum(rep_edits$event_type == "Other field-history event"))
)

Validation and AO2 interpretation

What the CRM data can establish: activity coverage, the prevalence of automated/integration events, REP-linked login patterns, and candidate opportunity-update activity. These measures can support AO1 adoption measurement and inform AO2’s behavioral context.

What the CRM data cannot establish on its own: perceived usefulness, ease of use, training quality, organizational barriers, or causal drivers of adoption. Those require a validated survey, interviews, or another appropriate source.

Important limitations:

  • role == "REP" identifies aliases ever associated with that role, not necessarily in that role on each event date.
  • Browser/Salesforce application matching is provisional, not a validated human-login classifier.
  • OppFieldHist rows are not necessarily independent human actions; some may be system-generated or duplicate representations.
  • Login data covers a limited period. Comparing raw login totals with full-history opportunity edits is not meaningful without harmonizing observation windows.
  • Avoid employee-level tables and small-cell disclosures in the public HTML.
